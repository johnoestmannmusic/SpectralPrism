## Project: SpectralPrism

**Project Title:** SpectralPrism — Spectral Freeze Instrument Plugin
**Project Description:** A Rust nih-plug/egui VST3/CLAP instrument that freezes a spectral snapshot of a loaded sample at a chosen "Freeze Point" and loops it indefinitely as a sustained pad/drone, shaped by Formant Shift, Stereo Width, Loop Length, and a full ADSR/velocity/pitch-bend/pan voice architecture.
**Implementation Repository:** this repository (`crates/prism_dsp`, `crates/prism_plugin`, `crates/prism_cli`, `xtask`).
**Board Last Updated:** 2026-09-11 15:24 by Claude Sonnet 5

### Ideas

#### SP-IDEA-001 — FM fusion mode ("waveforms act as operators")

- **Card Title:** FM fusion mode
- **Description:** A 10th Spectral Fusion algorithm where Sample A's and Sample B's frozen spectra modulate each other continuously (FM synthesis-style, "operators") rather than combining once. Architecturally bigger than every other Fusion mode shipped in SP-PLAN-001: those are all one-shot combines (either two `FrozenSpectrum`s combined once before resynthesis, or two fully-resynthesized audio buffers combined once after). FM instead needs one signal to continuously modulate the other's instantaneous phase/frequency *during* the per-hop resynthesis loop (`prism_dsp::resynth::FreezeResynth::next_frame`), which means changing the resynthesis engine itself (e.g. a second phase accumulator feeding into the first's phase advance every hop), not adding a sibling combine function next to `prism_dsp::fusion`'s existing ones. Deserves its own dedicated design pass rather than being bolted on.

#### SP-BUG-002 — Editor keyboard input broken/duplicated in embedded plugin windows (Linux, baseview)

- **Card Title:** Keyboard focus/autorepeat bugs in embedded editor (Linux)
- **Symptom:** Two related but distinct symptoms reported by the user across REAPER and Bespoke Synth on Linux, reproducing identically under both a Wayland session and a native X11/Xorg session (ruling out a Wayland-specific embedding-gap explanation - see process comments): (1) pressing Backspace in any editor text field (Preset name, Save dialog's Title/Author/Category/Sub-category, Preset Browser search) deletes more than one character per press, and (2) in a **freshly opened** editor instance, text fields don't accept keyboard input **at all** until *after* something else (confirmed: importing a preset, which opens/closes a native file-picker dialog) has caused the window to regain focus - after that point, typing works (modulo bug 1).
- **Root Cause:** Traced directly in the pinned `baseview` dependency's source (two git revs pinned via `nih_plug`/`egui-baseview`, both checked out locally and inspected - not guessed): (a) `src/x11/window.rs` - `Window::focus()` and `Window::has_focus()` were both literally `unimplemented!()` (would panic if ever called), and nothing in the window-creation/mapping path ever called `XSetInputFocus` - so there was no code path in `baseview` that actively requested keyboard focus for the window it creates, explaining symptom (2): the editor only got focus at all via an indirect side effect (a native dialog closing causes the window manager's own default transient-child focus-return behavior to kick in). (b) `src/x11/event_loop.rs` forwards every raw X11 `KeyPress`/`KeyRelease` straight through with no de-duplication, and `src/x11/keyboard.rs` hardcoded every event's `repeat` field to `false` regardless of whether X11's classic (non-"detectable") auto-repeat protocol behavior generated it - `egui-baseview` (`src/window.rs:521`) passes that flag straight to egui unchanged, so egui's `TextEdit` couldn't distinguish a genuine keypress from an auto-repeat-generated duplicate, explaining symptom (1). Confirmed a real upstream `baseview` bug, not something in SpectralPrism's own code - none of `prism_plugin`'s own code does any custom keyboard/focus handling.

#### SP-BUG-003 — Init preset's unload_samples panicked the render worker, leaving the previous sample's stale frozen loop playing forever

- **Card Title:** Init preset unload panicked the render worker
- **Description:** The user reported that loading the "Init" preset (unload_samples: true, see SP-PLAN-005) right after another preset with real samples loaded did *not* actually revert to the placeholder sine wave - the previous preset's frozen loop kept playing indefinitely. Root cause: `apply_preset`'s `unload_sample` closure stored a genuinely empty `Vec::new()` for Sample A, but `render_fused_loop`/`render_frozen_loop` (`prism_dsp`) always assume at least one channel (`.first().expect(...)`) and panic on empty input - unlike Sample B, which was already designed to safely support a fully-empty state via `effective_mode`'s graceful degrade. That panic happened *inside* `render_worker.rs`'s background thread closure, which had no panic guard - the thread silently died, permanently freezing `loop_buffer` (and every future render request, from *any* cause, not just Init) at whatever was last successfully rendered, with zero error surfaced anywhere. A serious, silent, session-ending bug traced directly to a real user bug report rather than being caught by testing beforehand.
- **Assigned Agent:** Claude Sonnet 5
- **Card Creation Date:** 2026-09-11 14:15
- **Card Completion Note:** Fixed at both levels. (1) `unload_sample` now takes an explicit `replacement: Vec<Vec<f32>>` parameter instead of hardcoding empty - Sample A's call site passes `vec![synthetic_source(sample_rate, 1.0)]` (mirroring `initialize()`'s own established placeholder-tone fallback), Sample B's still passes `Vec::new()` (its empty state was already correct/tested). (2) Hardened `render_worker.rs`'s background thread with `std::panic::catch_unwind` around the render call, so *any* future panic (from this bug's class or an unrelated one) logs to stderr and skips just that one render instead of silently killing the whole worker thread for the rest of the session - defense in depth, since a silent permanent freeze with no error message is a far worse failure mode than one skipped render. New regression test `worker_survives_a_panicking_render_and_processes_the_next_request` proves the worker stays alive and responsive to a subsequent valid request even after a request that would previously have killed it. Full workspace suite: 104/104 passing (83 `prism_dsp` + 21 `prism_plugin`, +1 new test). Release bundle rebuilt cleanly. Not verified via the standalone binary's actual GUI this round (the sandbox's throwaway X11 display from earlier sessions was gone, replaced by the user's real live desktop session, and running automated synthetic clicks against a real, currently-in-use desktop was judged too invasive to attempt) - verification instead rests on the new regression test directly proving the panic-survival mechanism, plus the fix's very close mirror of `initialize()`'s own already-proven placeholder-tone logic.
